### 유니캐스트, 멀티캐스트, 브로드캐스트, 애니캐스트

**유니캐스트**
- 1:1 통신
- 출발지와 목적지가 1:1로 통신
- 대부분의 일반적인 통신(웹 브라우징, 파일 전송 등)이 유니캐스트로 이루어짐
- 목적지 MAC 주소가 자신의 MAC 주소가 아닌 단말은 패킷을 받자마자 버리므로 다른 단말의 성능을 저하시키지 않음

**브로드캐스트**
- 1:모든 통신
- 동일 네트워크에 존재하는 모든 호스트가 목적지
- 유니캐스트로 통신하기 전, 주로 상대방의 정확한 위치를 알기 위해 사용 (ex. ARP 요청, DHCP Discover)
- 기본 동작은 로컬 네트워크 내에서 모든 호스트에 패킷을 전달해야 할 때 사용 됨
- 브로드캐스트 MAC 주소 : `FF:FF:FF:FF:FF:FF`
- 브로드캐스트 패킷은 받는 모든 단말이 CPU를 사용해 처리해야 하므로, 브로드캐스트가 많아지면 네트워크 전체의 성능이 저하됨
- 라우터(3계층 장비)는 브로드캐스트를 넘기지 않음 → 브로드캐스트가 전달되는 범위를 **브로드캐스트 도메인**이라고 함

**멀티캐스트**
- 1:그룹(멀티캐스트 구독 호스트) 통신
- 하나의 출발지에서 다수의 특정 목적지로 데이터 전송
- 사내 방송이나 증권 시세 전송과 같이 단방향으로 다수에게 동시에 같은 내용을 전달해야 할 때 사용됨
- IPv4 멀티캐스트 주소 대역 : `224.0.0.0 ~ 239.255.255.255` (D 클래스)
- 멀티캐스트 MAC 주소는 `01:00:5E`로 시작함
- 스위치는 IGMP 스누핑으로 멀티캐스트를 구독한 포트에만 패킷을 전달할 수 있음 (IGMP 스누핑이 없으면 브로드캐스트처럼 모든 포트로 전달됨)

**애니캐스트**
- 1:1 통신(목적지는 동일 그룹 내의 1개 호스트)
- 다수의 동일 그룹 중 가장 가까운 호스트에서 응답
- IPv4에서는 일부 기능 구현, IPv6은 모두 구현 가능
- 가장 가까운 DNS 서버를 찾을 때 사용하거나 가장 가까운 게이트웨이를 찾는 애니캐스트 게이트웨이 기능에 사용하기도 함
- 여러 위치의 서버가 같은 IP를 광고(BGP)하면 라우팅 상 가장 가까운 서버로 연결됨 → CDN, 퍼블릭 DNS(8.8.8.8, 1.1.1.1) 등에서 활용

**통신 방식 정리**

| 구분 | 통신 대상 | 목적지 | 주요 사용 예 |
| --- | --- | --- | --- |
| 유니캐스트 | 1:1 | 특정 호스트 1개 | 일반적인 데이터 통신 |
| 브로드캐스트 | 1:전체 | 같은 네트워크의 모든 호스트 | ARP, DHCP |
| 멀티캐스트 | 1:그룹 | 그룹에 가입한 호스트 | 사내 방송, 증권 시세, IPTV |
| 애니캐스트 | 1:1 (그룹 중 1개) | 그룹 중 가장 가까운 호스트 | DNS, CDN, 애니캐스트 게이트웨이 |

### MAC 주소

- MAC(Media Access Control)
- 2계층에서 사용하는 물리 주소

- MAC 주소는 변경할 수 없도록 하드웨어에 고정되어 출하되므로 네트워크 구성 요소마다 다른 주소를 가지고 있음
  - 단, 운영체제나 드라이버에서 소프트웨어적으로 MAC 주소를 변경해 사용할 수는 있음 (가상화 환경의 가상 MAC, 스마트폰의 MAC 랜덤화 등)
- 48비트의 16진수 12자리로 표현됨
  - 표기 예 : `00:1A:2B:3C:4D:5E`, `00-1A-2B-3C-4D-5E`, `001A.2B3C.4D5E`
- MAC 주소 앞의 24비트는 OUI(Organizational Unique Identifier)값 -> 제조사 코드 (IEEE에서 할당)
  - 뒤의 24비트의 값인 UAA(Universally Administrated Address) -> 각 제조사에서 네트워크 구성 요소에 할당하는 부분

```
  00 : 1A : 2B  :  3C : 4D : 5E
 |<-- OUI 24bit -->|<-- UAA 24bit -->|
    (제조사 코드)       (제조사가 할당)
```

**MAC 주소 동작**
- 2계층에서 데이터 형태(프레임)로 변환하여 내용을 구분한 후 도착지 MAC 주소를 확인함
- 만약 도착지 MAC 주소가 자신이 갖고 있는 MAC 주소와 다르면 그 패킷을 폐기함
- 패킷의 목적지 주소가 자기 자신이거나 브로드캐스트, 멀티캐스트와 같은 그룹 주소이면 처리해야 할 주소로 인지해 패킷 정보를 상위 계층으로 넘겨줌
- 단, 프로미스큐어스 모드(Promiscuous Mode)로 설정하면 목적지 MAC 주소와 관계없이 모든 패킷을 상위 계층으로 올림 (패킷 분석 도구 등에서 사용)

### IP 주소

- 사용자가 변경 가능한 논리 주소이다.
- 3계층에서 사용하는 주소
- 주소에 레벨이 있음. 그룹을 의미하는 네트워크 주소와 호스트 주소로 나뉨

**IP 주소 체계**

- IPv4 : 32비트
  - 8비트씩 4개의 옥텟(Octet)으로 나누고 각 옥텟을 10진수로 표기함 (0~255)
  - EX) `192.168.0.1`
- IPv6 : 128비트
  - 16비트씩 8개 블록으로 나누어 16진수로 표기하고 콜론(:)으로 구분함
  - 연속된 0은 `::`로 한 번만 생략 가능 EX) `2001:0db8:0000:0000:0000:0000:0000:0001` → `2001:db8::1`

- 네트워크 주소 : 호스트들을 모은 네트워크를 지칭하는 주소. 네트워크 주소가 동일한 네트워크를 로컬 네트워크라고 함
- 호스트 주소 : 하나의 네트워크 내에 존재하는 호스트를 구분하기 위한 주소

**네트워크와 호스트 이해하기**

- 네트워크는 **그룹**이고, 호스트는 그 그룹에 속한 **장비 한 대**임 (네트워크를 나눈 조각이 호스트인 것이 아님)
- 아파트 주소에 비유하면 네트워크 주소는 **동 번호**, 호스트 주소는 **호수**와 같음

```
  OO아파트  101동  1004호
 |<- 네트워크 주소 ->|<- 호스트 ->|
   (어느 동인지)     (그 동의 몇 호인지)
```

  - 101동 1004호와 101동 805호 → 같은 동 = 같은 네트워크(로컬 네트워크)
  - 101동 1004호와 102동 1004호 → 호수가 같아도 다른 동 = 다른 네트워크(게이트웨이를 거쳐 통신)

- IP 주소 하나에 네트워크 정보와 호스트 정보가 함께 들어 있음

```
192.168.1  .  10      (/24 기준)
|<-네트워크->| |<-호스트->|
```

| 장비 | IP | 네트워크 | 호스트 |
| --- | --- | --- | --- |
| 내 PC | 192.168.1.10 | 192.168.1 | 10 |
| 프린터 | 192.168.1.20 | 192.168.1 | 20 |
| 공유기 | 192.168.1.1 | 192.168.1 | 1 |

  - 세 장비는 모두 `192.168.1` 네트워크에 속한 서로 다른 호스트임
- IP 주소만으로는 어디까지가 네트워크인지 알 수 없으므로, 그 경계를 정하는 것이 **서브넷 마스크**임
  - `/24` : 앞 24비트가 네트워크, 나머지 8비트가 호스트 → 호스트 254대
  - `/16` : 앞 16비트가 네트워크, 나머지 16비트가 호스트 → 호스트 65,534대
  - 경계선을 뒤로 옮길수록 네트워크 하나의 크기와 그 안에 들어갈 수 있는 호스트 수가 줄어듦
- "나눈다"는 말은 두 가지 의미로 쓰이므로 구분해야 함
  1. IP 주소 하나를 네트워크 부분과 호스트 부분으로 나눔 → 주소를 읽는 방법
  2. 큰 네트워크를 작은 네트워크 여러 개로 나눔 → **서브네팅**. 나눈 결과도 여전히 네트워크(서브넷)이며 호스트가 되는 것이 아님

```
192.168.1.0/24 (네트워크 1개, 호스트 254대)
        ↓ 서브네팅 (/26으로 쪼개기)
192.168.1.0/26   192.168.1.64/26   192.168.1.128/26   192.168.1.192/26
(호스트 62대)    (호스트 62대)      (호스트 62대)       (호스트 62대)
```

- IP 주소 체계는 필요한 호스트 IP 개수에 따라 네트워크 크기를 다르게 할당할 수 있는 클래스 개념을 도입함
  - 주소를 절약할 수 있음

**클래스 구분법**

- 첫 번째 옥텟의 앞부분 비트로 클래스를 구분함

| 클래스 | 시작 비트 | 첫 옥텟 범위 | 기본 서브넷 마스크 | 사용 가능 호스트 수 |
| --- | --- | --- | --- | --- |
| A | 0 | 0 ~ 127 | 255.0.0.0 (/8) | 2^24 - 2 |
| B | 10 | 128 ~ 191 | 255.255.0.0 (/16) | 2^16 - 2 |
| C | 110 | 192 ~ 223 | 255.255.255.0 (/24) | 2^8 - 2 |
| D | 1110 | 224 ~ 239 | - | 멀티캐스트 |
| E | 1111 | 240 ~ 255 | - | 연구용 예약 |

- IP 체계에서 맨 앞의 숫자를 네트워크 주소로, 맨 뒤의 숫자를 브로드캐스트 주소로 사용하므로 실제로 사용할 수 있는 IP는 전체 개수에서 2개를 뺀 값임
  - EX) C 클래스 `192.168.1.0` 네트워크 → 네트워크 주소 `192.168.1.0`, 브로드캐스트 주소 `192.168.1.255`, 사용 가능 IP `192.168.1.1 ~ 192.168.1.254` (254개)
- 특징
  - 네트워크 주소와 호스트 주소를 구분짓는 구분자(서브넷 마스크)가 필요 없음
  - 맨 앞자리 숫자만 보면 자연스럽게 어느 클래스에 속해 있는지 구분할 수 있고 주소 구분자를 적용할 수 있음
  - 하지만 네트워크 크기가 A/B/C 3가지로만 고정되어 있어 유연하지 못하고 주소 낭비가 심함
    - EX) 300대의 호스트가 필요하면 C 클래스(254개)로는 부족해 B 클래스(65,534개)를 받아야 하므로 6만 개 이상의 주소가 낭비됨

**클래스리스 네트워크의 등장**

- 클래스풀 방식의 주소 낭비 문제를 해결하기 위해, 클래스와 관계없이 네트워크와 호스트를 나누는 기준을 자유롭게 정하는 클래스리스(CIDR, Classless Inter-Domain Routing) 방식이 등장함
- 서브넷 마스크 : 네트워크와 호스트 주소를 나누는 구분자
  - 2진수 숫자 1 : 네트워크 주소, 0은 호스트 주소
  - 1은 항상 연속되어야 함 (1과 0이 섞일 수 없음)
  - EX) 103.9.32.146 주소에 255.255.255.0 서브넷 마스크를 사용하는 IP는 네트워크 주소가 103.9.32.0이고, 호스트 주소는 0.0.0.146이 됨
- 네트워크 주소는 IP 주소와 서브넷 마스크를 2진수로 AND 연산하여 구함

```
IP 주소       103.9.32.146   = 01100111.00001001.00100000.10010010
서브넷 마스크  255.255.255.0  = 11111111.11111111.11111111.00000000
--------------------------------------------------------------------- AND
네트워크 주소  103.9.32.0     = 01100111.00001001.00100000.00000000
```

- 프리픽스 표기법 : 서브넷 마스크의 1의 개수를 `/` 뒤에 표기하는 방식
  - EX) `255.255.255.0` = `/24`, `103.9.32.146/24`

### 서브네팅

> 원래 부여된 클래스의 기준을 무시하고 새로운 네트워크-호스트 구분 기준을 사용자가 정해 원래 클래스풀 단위의 네트워크보다 더 쪼개 사용하는 것

- 네트워크 사용자 입장
  - 네트워크에서 사용할 수 있는 IP 범위 파악
  - 기본 게이트웨이와 서브넷 마스크 설정이 제대로 되어 있는지 확인

- 네트워크 설계자 입장
  - 네트워크 설계 시 네트워크 내에 필요한 단말을 고려한 네트워크 범위 설계
  - 필요한 호스트 수 + 2(네트워크, 브로드캐스트 주소)보다 큰 2의 제곱수 중 가장 작은 값으로 크기를 정함
    - EX) 호스트 50대 필요 → 50 + 2 = 52 → 2^6 = 64 → `/26`

- 서브네팅 방법 (예시 : `103.9.32.146/26`, 서브넷 마스크 `255.255.255.192`)
  1. 서브넷 마스크를 2진수로 변환한다.
     - `255.255.255.192` = `11111111.11111111.11111111.11000000`
  2. 현재 서브넷이 가질 수 있는 최대 IP 개수 크기를 파악한다. 호스트 비트(0)가 6개이므로 2^6 = 64
     - 간단히 `256 - 마지막 옥텟 마스크 값`으로도 구할 수 있다. 256 - 192 = 64
  3. 64의 배수로 나열하여 기준이 되는 네트워크 주소를 파악한다. 첫 블록은 0부터 시작한다. 각 네트워크의 마지막 주소가 브로드캐스트 주소가 된다. 이 주소는 다음 블록 네트워크 주소의 -1이다.
     - 0~63 / 64~127 / 128~191 / 192~255
  4. 103.9.32.146에서 호스트 주소 146이 속한 네트워크를 선택한다.
     - 128~191
  5. 필요한 주소를 정리한다.
     - 네트워크 주소 : 103.9.32.128 (첫 번째 숫자)
     - 브로드캐스트 주소 : 103.9.32.191(마지막 숫자)
     - 유효 IP 범위 : 103.9.32.129 ~ 103.9.32.190(네트워크 주소와 브로드캐스트 주소 사이)

**자주 사용하는 프리픽스 정리 (C 클래스 기준)**

### 공인 IP와 사설 IP

- 공인 IP : 전 세계에서 유일한 식별가능한 IP 주소
  - 인터넷 주소 관리 기관(IANA → 대륙별 RIR → 국가별 기관(한국은 KISA) → ISP)을 통해 할당받음
- 사설 IP : 인터넷에 연결하지 않고 개인적으로 네트워크를 구성해서 공인 IP 주소를 할당받지 않고 네트워크를 구축해서 사용하는 IP
  - 인터넷에 직접 접속하지 못하지만 IP를 변환해주는 NAT장비에서 공인 IP로 변경한 후에는 인터넷 접속이 가능함
  - 서로 다른 조직에서 같은 사설 IP 대역을 중복해서 사용할 수 있음 → IPv4 주소 고갈 문제 완화

**사설 IP 대역 (RFC 1918)**

| 클래스 | 대역 | 프리픽스 |
| --- | --- | --- |
| A | 10.0.0.0 ~ 10.255.255.255 | 10.0.0.0/8 |
| B | 172.16.0.0 ~ 172.31.255.255 | 172.16.0.0/12 |
| C | 192.168.0.0 ~ 192.168.255.255 | 192.168.0.0/16 |

**그 밖의 특수 목적 IP**

- `127.0.0.0/8` : 루프백 주소. 자기 자신을 가리킴 (주로 `127.0.0.1`, localhost)
- `169.254.0.0/16` : 링크 로컬 주소. DHCP 서버로부터 IP를 받지 못했을 때 자동으로 할당됨
- `0.0.0.0` : 아직 IP를 할당받지 못했거나, "모든 네트워크(디폴트 라우트)"를 의미
- `255.255.255.255` : 로컬 네트워크 전체에 대한 브로드캐스트 주소
- `100.64.0.0/10` : 통신사업자 NAT(CGNAT)용 공유 주소

**NAT (Network Address Translation)**

- 사설 IP를 공인 IP로(또는 반대로) 변환해주는 기술
- PAT(NAPT) : 여러 사설 IP를 하나의 공인 IP로 변환하고, 포트 번호로 각 세션을 구분하는 방식 → 가정용 공유기가 대표적
- 외부에서는 내부의 사설 IP가 보이지 않으므로 보안상 이점도 있음

### TCP와 UDP

- 4계층의 목적 : 목적지를 찾아가는 주소가 아니라 애플리케이션에서 사용하는 프로세스를 정확히 찾아가고 데이터를 분할한 패킷을 잘 쪼개 보내고 잘 조립하는 것
- 4계층에서는 **포트 번호**로 애플리케이션(프로세스)을 구분함 (16비트, 0 ~ 65535)
  - Well-Known 포트 (0 ~ 1023) : 잘 알려진 서비스용 (HTTP 80, HTTPS 443, SSH 22, DNS 53 등)
  - Registered 포트 (1024 ~ 49151) : 특정 애플리케이션용으로 등록된 포트 (MySQL 3306 등)
  - Dynamic 포트 (49152 ~ 65535) : 클라이언트가 통신할 때 임의로 사용하는 출발지 포트

**TCP**

- 신뢰할 수 없는 공용망에서도 정보유실 없는 통신을 보장하기 위해 세션을 안전하게 연결하고 데이터를 분할하고 분할된 패킷이 잘 전송되었는지 확인함
- 패킷에 번호를 부여하고 잘 전송되었는지에 대해 응답함
  - 시퀀스 번호(Sequence Number) : 보내는 데이터의 순서 번호
  - ACK 번호(Acknowledgement Number) : 다음에 받아야 할 데이터의 시퀀스 번호 (= 받은 데이터 + 1)
- 한꺼번에 얼마나 보내야 수신자가 잘 받아 처리할 수 있는지 전송 크기까지 고려해 통신

TCP 플래그
- `SYN` : 연결 시작 요청
- `ACK` : 응답 확인
- `FIN` : 연결 종료 요청
- `RST` : 연결 강제 초기화(비정상 종료)
- `PSH` : 버퍼링 없이 즉시 상위 계층으로 데이터 전달
- `URG` : 긴급 데이터 표시

윈도 사이즈와 슬라이딩 윈도
- TCP는 일방적으로 패킷을 보내는 것이 아니라 상대방이 얼마나 잘 받았는지 확인하기 위해 ACK 번호를 확인하고 다음 패킷을 전송함

- 패킷이 잘 전송되었는지 확인하기 위해 별도 패킷을 받는 것 자체가 통신 시간을 늘리지만 송신자와 수신자가 먼 거리에 떨어져 있으면 왕복 지연시간(RTT)이 늘어나므로 응답을 기다리는 시간이 더 길어짐
- 따라서 데이터를 보낼 때 패킷을 하나만 보내는 것이 아니라 많은 패킷을 한꺼번에 보내고 응답을 하나만 받음

윈도 사이즈 : 한 번에 데이터를 받을 수 있는 데이터 크기
- TCP 헤더의 윈도 사이즈 필드는 16비트이므로 최대 65,535바이트까지 표현 가능
- 고속/장거리 네트워크를 위해 윈도 스케일(Window Scale) 옵션으로 윈도 사이즈를 더 크게 확장할 수 있음

슬라이딩 윈도 : 네트워크 상황에 따라 윈도 사이즈를 조절 하는 것
- 수신 측이 처리할 수 있는 만큼 윈도 사이즈를 알려주어 송신 속도를 조절함 → **흐름 제어**
- 패킷 유실이 발생하면 네트워크가 혼잡하다고 판단해 윈도 사이즈를 줄이고, 정상이면 점차 늘림 → **혼잡 제어**


3WAY Handshake

- 목적지가 데이터를 받을 준비가 안 된 상황에서 데이터를 일방적으로 전송하면 목적지에서는 데이터를 정상적으로 처리할 수 없어 데이터가 버려짐
- 따라서, 유실없는 안전한 통신을 위해 통신 시작 전, 사전 연결작업을 진행함
- TCP에서는 3번의 패킷을 주고받으면서 통신을 준비함
  1. 출발지 → 목적지 : `SYN` (시퀀스 번호 x)
  2. 목적지 → 출발지 : `SYN + ACK` (시퀀스 번호 y, ACK 번호 x+1)
  3. 출발지 → 목적지 : `ACK` (ACK 번호 y+1) → 연결 수립(ESTABLISHED)

```
Client                          Server
  |  ------ SYN (seq=x) ------>   |   SYN_SENT
  |  <-- SYN+ACK (seq=y,ack=x+1)  |   SYN_RECEIVED
  |  ------ ACK (ack=y+1) ---->   |   ESTABLISHED
```

- 데이터를 윈도 사이즈로 보내고 메모리에 유지하다가 ACK 번호를 받은 후 통신이 잘 된 상황을 파악하고 나서야 메모리에서 데이터를 제거함
- 중간에 유실이 있으면 시퀀스 번호와 ACK 번호를 비교해가며 이를 파악하고 메모리에 유지해놓은 데이터를 이용해 재전송하는 기능이 있음

4WAY Handshake (연결 종료)

- 연결을 끊을 때는 양쪽이 각각 종료 의사를 전달해야 하므로 4번의 패킷을 주고받음
  1. 종료 요청 측 → 상대 : `FIN`
  2. 상대 → 종료 요청 측 : `ACK` (아직 보낼 데이터가 남아 있으면 마저 전송)
  3. 상대 → 종료 요청 측 : `FIN`
  4. 종료 요청 측 → 상대 : `ACK`
- 마지막 ACK를 보낸 쪽은 바로 연결을 닫지 않고 `TIME_WAIT` 상태로 일정 시간 대기함
  - 마지막 ACK가 유실되었을 때 재전송된 FIN에 응답하고, 늦게 도착한 패킷이 새 연결에 섞이는 것을 방지하기 위함

**UDP**

- 데이터 전송을 보장하지 않는 프로토콜임
- 연결 수립(핸드셰이크) 과정, 순서 보장, 재전송, 흐름/혼잡 제어가 없음
  - 대신 헤더가 8바이트로 작고(TCP는 최소 20바이트) 처리가 단순해 빠름
- 멀티캐스트처럼 단방향으로 다수의 단말과 통신해 응답을 받기 어려운 환경에서 주로 사용됨
  - 사내 방송, 증권 시세 데이터 전송, 음성, 동영상 등
- 중간에 데이터가 몇개쯤 유실되는 것보다 재전송하기 위해 잠시 동영상이나 음성이 멈추는 것을 더 이상하게 느낄 수 있기 때문
- 요청-응답이 짧게 끝나는 DNS, DHCP, SNMP 등에서도 사용됨
- 데이터 유실이 발생하면 필요에 따라 애플리케이션 계층에서 직접 처리해야 함 (EX. HTTP/3의 QUIC은 UDP 위에서 신뢰성을 구현)

**TCP vs UDP 정리**

| 구분 | TCP | UDP |
| --- | --- | --- |
| 연결 방식 | 연결형 (3way handshake) | 비연결형 |
| 신뢰성 | 보장 (ACK, 재전송) | 보장하지 않음 |
| 순서 보장 | O (시퀀스 번호) | X |
| 흐름/혼잡 제어 | O (슬라이딩 윈도) | X |
| 헤더 크기 | 20 ~ 60 바이트 | 8 바이트 |
| 속도 | 상대적으로 느림 | 빠름 |
| 통신 방식 | 유니캐스트 | 유니캐스트, 멀티캐스트, 브로드캐스트 |
| 사용 예 | HTTP, SSH, FTP, SMTP | DNS, DHCP, 스트리밍, VoIP |

### ARP (Address Resolution Protocol)

> 상대방의 MAC 주소를 알아내기 위해 사용되는 프로토콜

- IP 주소 체계는 물리적 MAC 주소와 전혀 연관성이 없으므로 두 개의 주소를 연계시켜 주기 위한 메커니즘이 필요함
- ARP 브로드캐스트를 이용해 네트워크 전체에 상대방의 MAC 주소를 질의해야 함

- 동작 과정
  - 서버 A는 목적지 서버 B의 MAC 주소를 알아내기 위해 ARP 요청을 네트워크에 브로드캐스트 함
    - 이때 목적지 MAC 주소는 `FF:FF:FF:FF:FF:FF`, ARP 패킷 내 대상자 MAC 주소는 아직 모르므로 `00:00:00:00:00:00`으로 채움
  - 모든 단말은 ARP 프로토콜 내용을 확인하는데 ARP 프로토콜 필드의 대상자 IP가 자신이 맞는지 확인해 자신이 아니면 ARP 패킷을 버림
  - 서버 B에서는 ARP 요청의 대상자 IP 주소가 자신의 IP이므로 ARP 요청을 처리하고 그에 대한 응답을 보냄
  - ARP 응답을 보낼 떄는 출발지와 도착지 MAC 주소가 명시되어 있는 유니캐스트 임
  - 서버 A는 서버 B로부터 ARP 응답을 받아 자신의 ARP 캐시 테이블을 갱신함

- ARP 패킷의 주요 필드
  - Operation Code : 1 = ARP 요청, 2 = ARP 응답
  - Sender MAC / Sender IP : 보내는 쪽의 MAC, IP 주소
  - Target MAC / Target IP : 대상자의 MAC, IP 주소

**ARP 캐시 테이블**

- 통신할 때마다 ARP 브로드캐스트를 보내면 네트워크 부하가 커지므로, 알아낸 IP-MAC 매핑 정보를 일정 시간 동안 메모리(ARP 캐시 테이블)에 저장해 재사용함
- 일정 시간(OS마다 다름, 수십 초 ~ 수 분) 동안 사용하지 않으면 테이블에서 삭제되고, 다시 통신할 때 ARP 요청을 보냄
- `arp -a` 명령어로 현재 ARP 캐시 테이블을 확인할 수 있음

**ARP의 보안 취약점**

- ARP는 응답이 정상적인지 검증하는 절차가 없음
- 공격자가 위조된 ARP 응답을 보내 다른 단말의 ARP 테이블을 조작하는 **ARP 스푸핑**이 가능 → 중간자 공격(MITM)에 악용됨
- 스위치의 DAI(Dynamic ARP Inspection) 기능이나 정적 ARP 설정으로 대응할 수 있음

### GARP (Gratuitous ARP)

- 대상자 IP  필드에 자신의 IP 주소를 채워 ARP 요청을 보냄
  - 일반 ARP는 상대방의 MAC 주소를 묻는 것이지만, GARP는 "이 IP는 나의 MAC 주소야"라고 알리는 것
- 자신의 IP와 MAC 주소를 알릴 목적으로 사용됨
- 로컬 네트워크에 자신의 IP와 MAC 주소를 알릴 목적으로 사용되므로 GARP 목적지 MAC 주소는 브로드캐스트 MAC 주소를 사용함
- 역할
  - IP 주소 충돌 감지
  - 상대방(동일 서브넷 상의 다른)의 ARP 테이블 갱신
  - HA(고가용성) 용도의 클러스터링, VRRP, HSRP

**IP 충돌 감지**

- 여러가지 이유로 내가 할당받은 IP를 다른 사람이 사용하고 있을 수 있음. IP 충돌 때문에 통신이 안 되는 것을 예방하기 위해 자신에게 할당된 IP가 네트워크에서 이미 사용되고 있는지 GARP를 통해 확인
- 단말이 네트워크에 연결되면 GARP를 통해 현재 설정된 IP 주소를 네트워크에서 사용하고 있는지 확인할 수 있음
- GARP에 대한 응답이 오면 같은 IP를 사용하는 다른 단말이 있다는 의미이므로 IP 충돌 경고를 띄움

**상대방(동일 서브넷 상의 다른)의 ARP 테이블 갱신**

- 가상 MAC 주소를 사용하지 않는 데이터베이스 HA 솔루션에서 주로 사용함
- 주로 두 데이터베이스 서버가 하나의 가상 IP주소로 서비스함
  - 두 대의 데이터 베이스 중 한 대만 동작하고 나머지 한 대는 대기하는 액티브-스탠바이로 동작함
  - 액티브 상태인 서버가 가상 IP 주소 요청에 응답해 서비스하지만 MAC 주소는 가상 주소가 아닌 실제 MAC 주소를 사용함
- 액티브 서버에 장애가 발생해 스탠바이 서버가 가상 IP를 넘겨받으면, 다른 단말들의 ARP 테이블에는 여전히 이전 서버의 MAC 주소가 남아 있음
  - 새로 액티브가 된 서버가 GARP를 보내 가상 IP에 대한 MAC 주소가 자신으로 바뀌었음을 알림
- 단말의 ARP 테이블을 갱신하는 것이 목적

**클러스터링, VRRP(Virtual Router Redundancy Protocol), HSRP(Hot Standby Router Protocol)**

- 네트워크에 있는 스위치 장비의 MAC 테이블 갱신이 목적
- VRRP, HSRP는 FHRP(First Hop Redundancy Protocol)의 일종
  - VRRP : 표준 프로토콜, 가상 MAC 주소 `00:00:5E:00:01:{VRID}`
  - HSRP : 시스코 전용 프로토콜, 가상 MAC 주소 `00:00:0C:07:AC:{그룹 번호}`
- 디폴트 게이트웨이에 장애가 발생할 경우, 해당 네트워크에 속한 단말이 외부 네트워크로 통신할 수 없는 문제를 해결하기 위해 개발됨
- 단독으로 경로 지정을 할 수 없는 PC는 디폴트 게이트웨이의 상태를 알 수 없으므로 두 대의 디폴트 게이트웨이 라우터가 한 대처럼 동작해 한 대에 문제가 생기더라도 다른 한 대에서 서비스를 지속할 수 있는 FHRP를 사용해야함
- 두 라우터가 가상 IP와 가상 MAC 주소를 공유하므로, 장애가 발생해도 단말의 ARP 테이블은 바꿀 필요가 없음
  - 하지만 가상 MAC 주소가 연결된 스위치 포트가 바뀌므로 스위치의 MAC 테이블은 갱신해야 함
- 슬레이브가 마스터로 역할이 변경되면 GARP를 전송하고 스위치에서는 이 GARP를 통해 MAC 주소에 대한 포트 정보를 새로 변경해 MAC 테이블을 갱신함


**RARP(Reverse ARP)**

- RARP는 IP 주소가 정해져 있지 않은 단말이 IP 할당을 요청할 때 사용함
- 나 자신의 MAC 주소는 알지만 IP가 아직 할당되지 않아 IP를 할당해주는 서버에 어떤 IP 주소를 써야 하는지 물어볼 때 사용됨
- 과거에 네트워크 호스트의 주소 할당에 사용되었지만 제한된 기능으로 인해 BOOTP와 DHCP로 대체되어 사용되지 않음
  - RARP는 IP 주소만 알려줄 수 있고 서브넷 마스크, 게이트웨이, DNS 등의 정보는 전달할 수 없음
  - 2계층 프로토콜이라 라우터를 넘어가지 못해 네트워크마다 RARP 서버가 필요했음

| 구분 | ARP | GARP | RARP |
| --- | --- | --- | --- |
| 목적 | 상대 IP로 MAC 주소 알아내기 | 내 IP와 MAC 주소 알리기 | 내 MAC으로 IP 주소 알아내기 |
| 대상자 IP | 상대방 IP | 자신의 IP | - |
| 주요 사용 | 일반 통신 전 MAC 확인 | IP 충돌 감지, HA 절체 | (현재는 DHCP로 대체) |


### 서브넷과 게이트웨이

게이트웨이 : 원격지 네트워크와 통신에 사용하는 장비 (3계층 장비(라우터와 L3 스위치)가 이 역할을 함)

- 브로드캐스트는 원격지 네트워크로 보낼 수 없음
- 출발지와 목적지 네트워크가 동일한 LAN 내에서 통신하는 것인지, 서로 다른 네트워크 간의 통신인지에 따라 통신 방식이 달라지므로 출발지에서는 먼저 목적지가 자신이 속한 네트워크 범위인지 확인하는 작업이 필요함
- 용도
  - 원격 네트워크 통신 : 로컬 네트워크를 벗어나는 모든 패킷은 게이트웨이를 거쳐 전달됨
  - 서로 다른 네트워크(서브넷) 간 패킷 전달(라우팅)
- 단말에 설정해야 하는 정보
  - IP 주소, 서브넷 마스크, 기본 게이트웨이(디폴트 게이트웨이)
  - 기본 게이트웨이는 보통 해당 네트워크에서 사용 가능한 첫 번째 IP(EX. `192.168.1.1`)나 마지막 IP(EX. `192.168.1.254`)를 사용하는 경우가 많음

**목적지가 로컬 네트워크인지 판단하는 방법**

- 자신의 IP와 목적지 IP를 각각 자신의 서브넷 마스크로 AND 연산해 나온 네트워크 주소가 같은지 비교함
  - 같으면 로컬 네트워크 → 목적지로 직접 통신
  - 다르면 원격지 네트워크 → 기본 게이트웨이로 전달

```
내 IP       : 192.168.1.10/24  → 네트워크 주소 192.168.1.0
목적지 IP 1 : 192.168.1.20     → 네트워크 주소 192.168.1.0  (같음 → 로컬 통신)
목적지 IP 2 : 10.10.10.5       → 네트워크 주소 10.10.10.0   (다름 → 게이트웨이로)
```

**2계층 통신(로컬 네트워크 통신) VS 3계층 통신(원격지 네트워크 통신)**

- 같은 네트워크에 있는 단말 간 통신은 직접적으로 이루어짐
- 상대방의 MAC 주소를 알아내기 위해 ARP 브로드캐스트를 이용하고 상대방의 MAC 주소를 알아내자마자 패킷이 캡슐화되어 통신이 시작됨
- 외부 네트워크와 통신이 필요할 때는 단말이 자신이 직접 보낼 수 없는 위치에 목적지가 있다고 판단하고 ARP 요청을 기본 게이트웨이의 IP 주소로 요청함
  - 도착지 MAC 주소에 응답받은 기본 게이트웨이의 MAC 주소를 적어놓고 통신을 시작함
- 로컬 통신은 도착지 MAC 주소와 도착지 IP주소가 같은 단말의 주소인 반면, 원격지 통신은 도착지 MAC 주소(게이트웨이)와 도착지 IP 주소(최종 목적지)가 서로 다른 단말의 주소임
- 원격지 통신에서 패킷이 라우터를 하나씩 지날 때마다(홉) 출발지/도착지 MAC 주소는 계속 바뀌지만, 출발지/도착지 IP 주소는 바뀌지 않음 (NAT를 거치는 경우는 제외)

| 구분 | 로컬 네트워크 통신 | 원격지 네트워크 통신 |
| --- | --- | --- |
| ARP 요청 대상 | 목적지 IP | 기본 게이트웨이 IP |
| 도착지 MAC 주소 | 목적지 단말의 MAC | 기본 게이트웨이의 MAC |
| 도착지 IP 주소 | 목적지 단말의 IP | 최종 목적지 단말의 IP |
| 경유 장비 | 스위치(2계층) | 라우터/L3 스위치(3계층) |
